TAKOUBAKOY LAB — EXPÉRIMENTATION 03

Laboratoire réseau
Docker & Nginx

Création d'un réseau Docker privé, communication entre conteneurs et validation d'un serveur web local.

OBJECTIF

1. Objectif de l'expérimentation

Cette expérimentation vise à comprendre le fonctionnement d'un réseau Docker de type bridge et à vérifier la communication entre deux conteneurs Linux.

Un serveur web Nginx est déployé dans un conteneur, puis interrogé depuis un second conteneur Alpine. L'accès HTTP depuis Windows est également testé au moyen d'une publication de port sur l'interface locale.

ENVIRONNEMENT

2. Configuration technique

  • Système hôte : Windows 11 Famille.
  • Terminal : Windows PowerShell 5.1.
  • Plateforme : Docker Desktop avec moteur WSL 2.
  • Réseau Docker : takoubakoy-lab-net.
  • Pilote réseau : bridge.
  • Serveur : lab-server, image nginx:alpine.
  • Client : lab-client, image alpine:latest.
  • Port HTTP interne : 80/tcp.
  • Publication locale : 127.0.0.1:8080 vers le port 80.

ARCHITECTURE

3. Architecture réseau

Les deux conteneurs sont connectés au même réseau Docker défini par l'utilisateur. Ils peuvent communiquer au moyen de leurs noms grâce à la résolution DNS interne. 

Windows 11
    |
    | http://127.0.0.1:8080
    |
Docker Desktop / WSL 2
    |
    +-- takoubakoy-lab-net (bridge)
          |
          +-- lab-server
          |     nginx:alpine
          |     HTTP : port 80
          |
          +-- lab-client
                alpine:latest
                ping / wget

Le port 8080 est publié sur l'adresse de boucle locale 127.0.0.1. Le service est ainsi destiné aux tests depuis la machine hôte, sans publication volontaire sur les interfaces réseau externes.

PROCÉDURE

4. Déploiement du laboratoire

4.1 — Inventaire des réseaux

docker network ls

Les réseaux standards bridge, host et none ont été observés.

4.2 — Création du réseau privé

docker network create takoubakoy-lab-net

Le réseau takoubakoy-lab-net a été créé avec le pilote bridge et la portée local.

4.3 — Déploiement initial du serveur

docker run -d --name lab-server --network takoubakoy-lab-net nginx:alpine

L'image Nginx Alpine a été téléchargée et le conteneur lab-server a démarré.

4.4 — Déploiement du client

docker run -dit --name lab-client --network takoubakoy-lab-net alpine:latest sh

Le conteneur lab-client a été démarré sur le même réseau privé.

4.5 — Publication locale du serveur

Après les tests internes, le serveur initial a été supprimé puis recréé avec une publication de port limitée à l'interface locale. 

docker rm -f lab-server

docker run -d --name lab-server --network takoubakoy-lab-net -p 127.0.0.1:8080:80 nginx:alpine

RÉSULTATS

5. Tests et mesures

Test 1 — État des conteneurs

docker ps

Résultat : les conteneurs lab-server et lab-client ont été observés à l'état Up.

Test 2 — Résolution DNS et connectivité ICMP

docker exec lab-client ping -c 4 lab-server

Le nom lab-server a été résolu vers l'adresse IPv4 172.18.0.2 lors du test initial.

  • Paquets transmis : 4.
  • Paquets reçus : 4.
  • Perte de paquets : 0 %.
  • Latence minimale : 0,092 ms.
  • Latence moyenne : 0,134 ms.
  • Latence maximale : 0,251 ms.

Résultat : résolution DNS et connectivité ICMP validées entre les conteneurs.

Test 3 — Communication HTTP interne

docker exec lab-client wget -qO- http://lab-server

Le client Alpine a récupéré le document HTML de la page d'accueil Nginx, contenant le titre Welcome to nginx!.

Résultat : communication HTTP interne validée.

Test 4 — Accès depuis Microsoft Edge

L'adresse http://127.0.0.1:8080 a été ouverte dans Microsoft Edge sous Windows.

La page d'accueil Nginx s'est affichée correctement.

Test 5 — Vérification des en-têtes HTTP

curl.exe -I http://127.0.0.1:8080

Résultats observés :

  • Code HTTP : 200 OK.
  • Serveur : nginx/1.31.8.
  • Content-Type : text/html.
  • Content-Length : 896 octets.
  • Connection : keep-alive.

Résultat : le serveur HTTP local répond correctement.

ANALYSE

6. Observations et limites

  • Le réseau bridge défini par l'utilisateur permet la communication entre les conteneurs qui y sont connectés.
  • La résolution DNS interne permet de joindre lab-server sans saisir directement son adresse IP.
  • Les latences ICMP relevées correspondent à une session de test locale et ne constituent pas une mesure générale des performances Docker.
  • L'adresse IP d'un conteneur peut changer après sa recréation.
  • La publication sur 127.0.0.1 limite l'écoute à l'interface locale, sans constituer à elle seule une garantie complète de sécurité du système.
  • Aucun test de charge, de segmentation avancée ou de résistance aux attaques n'a été réalisé.

CONCLUSION

7. Conclusion technique

L'expérimentation 03 confirme le fonctionnement d'un laboratoire réseau Docker local reposant sur deux conteneurs Linux et un réseau privé bridge.

La résolution DNS, la communication ICMP, la récupération d'une page HTTP depuis un conteneur et l'accès local depuis Windows ont été vérifiés.

Le serveur Nginx a répondu avec le code HTTP 200 OK, confirmant le fonctionnement de la publication locale du service.

Ces résultats constituent une base pour de futures expérimentations sur les services web, les réseaux de conteneurs et les infrastructures numériques maîtrisées.
