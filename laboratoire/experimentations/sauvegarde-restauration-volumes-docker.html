TAKOUBAKOY LAB — EXPÉRIMENTATION 05

Sauvegarde et restauration
des volumes Docker

Protection des données persistantes, création d'archives et restauration d'une infrastructure WordPress et MariaDB dans de nouveaux volumes Docker.

OBJECTIF

1. Objectif de l'expérimentation

Cette expérimentation vise à maîtriser les opérations de sauvegarde et de restauration des données persistantes utilisées par des applications conteneurisées.

Le laboratoire s'appuie sur l'environnement WordPress et MariaDB déployé lors de l'expérimentation 04.

Les données des deux volumes Docker sont exportées dans des archives compressées, puis restaurées dans de nouveaux volumes indépendants.

L'objectif final est de vérifier l'intégrité des fichiers, le fonctionnement de la base de données restaurée et la disponibilité de l'application WordPress.

ENVIRONNEMENT

2. Configuration technique

  • Système hôte : Windows 11 Famille.
  • Terminal : Windows PowerShell 5.1.
  • Plateforme : Docker Desktop avec moteur WSL 2.
  • Base de données : MariaDB 11.4.
  • Application web : WordPress avec PHP 8.3 et Apache.
  • Outil d'archivage : tar.
  • Image utilitaire : Alpine Linux 3.22.
  • Format des sauvegardes : archives TAR compressées GZIP.
  • Stockage : volumes Docker nommés.
  • Accès local de restauration : 127.0.0.1:8082.

ARCHITECTURE

3. Architecture de sauvegarde et restauration

L'expérimentation repose sur deux volumes sources issus du déploiement WordPress et MariaDB de l'expérimentation 04. 

ENVIRONNEMENT SOURCE
    |
    +-- experiment-04-compose_db_data
    |       Données MariaDB
    |
    +-- experiment-04-compose_wordpress_data
            Fichiers WordPress

                |
                | Sauvegarde TAR + GZIP
                v

ARCHIVES DE SAUVEGARDE
    |
    +-- wordpress-data.tar.gz
    |
    +-- mariadb-data.tar.gz

                |
                | Extraction
                v

NOUVEAUX VOLUMES DOCKER
    |
    +-- experiment-05-restore-wordpress
    |
    +-- experiment-05-restore-mariadb

                |
                | Démarrage des services
                v

ENVIRONNEMENT RESTAURÉ
    |
    +-- MariaDB 11.4
    |
    +-- WordPress / PHP 8.3 / Apache
    |
    +-- Réseau : experiment-05-restore-net
    |
    +-- Accès : http://127.0.0.1:8082

Les volumes restaurés sont indépendants des volumes sources. Cette séparation permet de tester la récupération des données sans modifier l'installation d'origine.

PROCÉDURE

4. Procédure de sauvegarde et restauration

4.1 — Préparation de l'environnement

Un dossier indépendant a été créé pour stocker les archives de sauvegarde. 

New-Item -ItemType Directory -Force -Path "$HOME\TAKOUBAKOY-LAB\experiment-05-backup-restore"

Les conteneurs sources ont été arrêtés et retirés, tout en conservant les volumes persistants.

4.2 — Vérification des volumes sources

docker volume inspect experiment-04-compose_db_data experiment-04-compose_wordpress_data

Les deux volumes sources ont été identifiés et leur disponibilité confirmée.

4.3 — Sauvegarde des fichiers WordPress

docker run --rm `
  -v experiment-04-compose_wordpress_data:/source:ro `
  -v "$HOME\TAKOUBAKOY-LAB\experiment-05-backup-restore:/backup" `
  alpine:3.22 `
  tar -czf /backup/wordpress-data.tar.gz -C /source .

Le volume WordPress est monté en lecture seule. Son contenu est exporté dans une archive compressée.

4.4 — Sauvegarde de MariaDB

docker run --rm `
  -v experiment-04-compose_db_data:/source:ro `
  -v "$HOME\TAKOUBAKOY-LAB\experiment-05-backup-restore:/backup" `
  alpine:3.22 `
  tar -czf /backup/mariadb-data.tar.gz -C /source .

Les fichiers de la base de données sont exportés dans une seconde archive indépendante.

Les deux volumes sources sont montés en lecture seule pendant les opérations de sauvegarde.

4.5 — Vérification des archives

Get-ChildItem "$HOME\TAKOUBAKOY-LAB\experiment-05-backup-restore" |
Select-Object Name, Length, LastWriteTime

Archives obtenues :

  • wordpress-data.tar.gz : 36 948 151 octets.
  • mariadb-data.tar.gz : 2 546 972 octets.

La lecture du contenu des archives a été vérifiée avec tar -tzf. 

docker run --rm `
  -v "$HOME\TAKOUBAKOY-LAB\experiment-05-backup-restore:/backup:ro" `
  alpine:3.22 `
  sh -c "tar -tzf /backup/wordpress-data.tar.gz > /dev/null && echo 'WORDPRESS: ARCHIVE OK' && tar -tzf /backup/mariadb-data.tar.gz > /dev/null && echo 'MARIADB: ARCHIVE OK'"

Résultat observé :

WORDPRESS: ARCHIVE OK
MARIADB: ARCHIVE OK

4.6 — Création des volumes de restauration

docker volume create experiment-05-restore-wordpress

docker volume create experiment-05-restore-mariadb

Deux nouveaux volumes ont été créés pour recevoir les données restaurées.

4.7 — Restauration de WordPress

docker run --rm `
  -v experiment-05-restore-wordpress:/destination `
  -v "$HOME\TAKOUBAKOY-LAB\experiment-05-backup-restore:/backup:ro" `
  alpine:3.22 `
  tar -xzf /backup/wordpress-data.tar.gz -C /destination

4.8 — Restauration de MariaDB

docker run --rm `
  -v experiment-05-restore-mariadb:/destination `
  -v "$HOME\TAKOUBAKOY-LAB\experiment-05-backup-restore:/backup:ro" `
  alpine:3.22 `
  tar -xzf /backup/mariadb-data.tar.gz -C /destination

Les deux archives ont été extraites dans leurs volumes de destination respectifs.

RÉSULTATS

5. Tests et vérifications

Test 1 — Comparaison des volumes

Les tailles des répertoires sources et restaurés ont été comparées.

  • WordPress original : 121,3 Mo.
  • WordPress restauré : 121,3 Mo.
  • MariaDB originale : 159,3 Mo.
  • MariaDB restaurée : 159,3 Mo.

Résultat : les tailles occupées sont identiques.

Test 2 — Comparaison des fichiers

Une comparaison récursive a été réalisée entre les répertoires sources et restaurés avec la commande diff -qr.

  • WordPress : code de sortie 0.
  • MariaDB : code de sortie 0.
  • Différences détectées : aucune.

Résultat : les fichiers des volumes restaurés sont identiques aux fichiers sources au moment de cette comparaison.

Test 3 — Démarrage de MariaDB restaurée

Un nouveau conteneur MariaDB 11.4 a été démarré en utilisant exclusivement le volume restauré. 

docker run -d `
  --name takoubakoy-restore-db `
  -e MARIADB_ROOT_PASSWORD=[MOT_DE_PASSE_DE_TEST] `
  -v experiment-05-restore-mariadb:/var/lib/mysql `
  mariadb:11.4

Le journal du serveur a confirmé le démarrage et la disponibilité du service. 

mariadbd: ready for connections.

Résultat : MariaDB restaurée opérationnelle.

Test 4 — Vérification de la base WordPress

La base wordpress a été retrouvée dans l'instance MariaDB restaurée.

Les douze tables WordPress ont été identifiées, notamment :

  • wp_users
  • wp_usermeta
  • wp_posts
  • wp_postmeta
  • wp_options
  • wp_comments
  • wp_commentmeta
  • wp_terms
  • wp_term_taxonomy
  • wp_term_relationships
  • wp_termmeta
  • wp_links

Résultat : structure de la base WordPress restaurée et accessible.

Test 5 — Vérification du compte administrateur

Le compte administrateur a été retrouvé dans la table wp_users.

  • ID : 1.
  • Identifiant : labadmin.
  • Statut : 0 (actif).

Résultat : compte administrateur présent dans la base restaurée.

Test 6 — Démarrage de WordPress restauré

Un nouveau conteneur WordPress avec PHP 8.3 et Apache a été démarré avec le volume restauré. Il a été relié au conteneur MariaDB au moyen d'un réseau Docker dédié. 

docker network create experiment-05-restore-net

docker network connect experiment-05-restore-net takoubakoy-restore-db

Le service WordPress a été publié sur le port local 8082, indépendamment de l'environnement source. 

docker run -d `
  --name takoubakoy-restore-wordpress `
  --network experiment-05-restore-net `
  --network-alias wordpress `
  -p 127.0.0.1:8082:80 `
  -e WORDPRESS_DB_HOST=takoubakoy-restore-db:3306 `
  -e WORDPRESS_DB_USER=wpuser `
  -e WORDPRESS_DB_PASSWORD=[MOT_DE_PASSE_DE_TEST] `
  -e WORDPRESS_DB_NAME=wordpress `
  -v experiment-05-restore-wordpress:/var/www/html `
  wordpress:php8.3-apache

Résultat : les deux conteneurs restaurés ont été observés à l'état Up.

Test 7 — Accès HTTP à l'application restaurée

Après adaptation des paramètres d'adresse du site dans la base restaurée pour son accès sur le port 8082, une requête HTTP a été réalisée. 

curl.exe -I http://127.0.0.1:8082

Résultat observé :

HTTP/1.1 200 OK
Server: Apache/2.4.69 (Debian)
X-Powered-By: PHP/8.3.36
Content-Type: text/html; charset=UTF-8

Le site WordPress restauré s'est également affiché correctement dans Microsoft Edge.

Résultat : restauration fonctionnelle et accès web validé.

ANALYSE

6. Observations techniques

  • Les volumes Docker permettent de séparer les données persistantes du cycle de vie des conteneurs.
  • Les archives TAR compressées facilitent le transport et la conservation des données.
  • Le montage en lecture seule des volumes sources permet de réaliser les sauvegardes sans modifier les données d'origine.
  • La restauration dans de nouveaux volumes permet de tester la récupération indépendamment de l'environnement source.
  • La comparaison récursive des fichiers confirme l'identité des données restaurées au moment du contrôle.
  • Le démarrage de MariaDB et de WordPress à partir des volumes restaurés confirme leur exploitabilité dans un nouvel environnement de conteneurs.
  • Une sauvegarde de fichiers de base de données doit être réalisée lorsque le serveur est arrêté ou selon une méthode garantissant la cohérence des données.

CONCLUSION

7. Conclusion technique

L'expérimentation 05 confirme la capacité à sauvegarder et restaurer les volumes persistants d'une application composée de WordPress et MariaDB.

Les archives ont été vérifiées, les données restaurées dans de nouveaux volumes et leur identité confirmée par comparaison récursive des fichiers.

Le serveur MariaDB restauré a démarré correctement. La base wordpress, ses douze tables et le compte administrateur ont été retrouvés.

Enfin, le conteneur WordPress restauré a communiqué avec MariaDB et le site a répondu avec le code HTTP 200 OK.

Cette expérimentation démontre la maîtrise d'une procédure de sauvegarde et de restauration des données Docker, compétence essentielle pour la continuité et la récupération des services numériques.
